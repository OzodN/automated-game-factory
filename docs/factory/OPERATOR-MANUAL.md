# Operator manual — Game Production Factory

## 1. One-time setup
1. Open Claude Code in the cloned repository folder. The session starts as **game-orchestrator**. Talk to it in your own language: `humanLanguage` in `factory/config.json` (or env `FACTORY_HUMAN_LANGUAGE`) is `auto` by default (the orchestrator replies in the language you write in); set it to a code such as `en` or `ru` to fix the language. Artifacts, code and subagent prompts stay English.
2. Run `node factory/cli/factory.mjs doctor` and fix every `FAIL` (and every `WARN`, see section 5). Besides tools and disk space it checks the pinned models, model env overrides (environment and the `env` blocks of `.claude/settings.json` / `.claude/settings.local.json`), the human language setting and that hard links can be created in the state directory (`.factory/` or `FACTORY_STATE_DIR`). Run markers and port reservations need hard links, so keep the factory on a local filesystem with hard links (NTFS, APFS, ext4 and similar), not FAT/exFAT or a network share.
3. Playgama: in Claude Code type `/mcp` → `plugin:playgama-developer-cabinet:playgama` → Authenticate (browser OAuth; never paste passwords or tokens in chat). Agents can be revoked at developer.playgama.com/mcp.
4. Asset library: create a folder anywhere on a local disk, optionally a synced one (e.g. Google Drive for desktop: `G:\My Drive\game-asset-library` on Windows, `~/Library/CloudStorage/GoogleDrive-<account>/My Drive/game-asset-library` on macOS). Point the factory at it with the environment variable `GAME_ASSET_LIBRARY` or with `"assetLibrary": "<folder>"` in `factory/config.json` (the variable wins). Setting the variable: on Windows, a user environment variable (System Properties → Environment Variables, or `setx GAME_ASSET_LIBRARY "<folder>"`); on macOS/Linux, `export GAME_ASSET_LIBRARY="<folder>"` in your shell profile (`~/.zshrc`, `~/.bashrc`). Restart Claude Code afterwards. Without either setting a local fallback library is used (`factory assets where` shows which one).
5. Seed the library: download CC0 packs manually (Kenney, OpenGameArt and itch.io block automated downloads) into a folder and ask the orchestrator to ingest them, e.g. "Add the pack Kenney Interface Sounds from ~/Downloads/kenney_interface-sounds.zip (CC0) to the library". Every pack is license-checked before use.

## 2. Lifecycle and your commands
| Stage | What the factory does | You type |
|---|---|---|
| Ideation | designer + analyst + architect produce and critique the Game Concept Brief | discuss freely; then `/approve-concept` |
| Specification | GDD, tech design, art/audio, Playgama integration, test plan | `/approve-spec` |
| Start | spec frozen, repo scaffolded, phase plan + task DAG | `/start-development` |
| Each phase | parallel tasks in isolated worktrees → deterministic verify → independent review → integration → checkpoint report | `/approve-phase` · `/reject-phase <reason>` · `/request-changes <text>` · `/pause` |
| Blocked task | blocker report with root cause and proposal | `/retry-task <ID>` · `/abandon-task <ID>` · `/modify-requirements <text>` |
| Playtest | release candidate served locally + scenarios + QA report | `/approve-playtest` · `/reject-playtest <issues>` |
| Release | merge to main, tag, deterministic zip, validation, archive | `/approve-release 1.0.0` |
| Publication | covers (`factory publish covers`, real screenshots of the packaged build) + packet (form texts, covers referenced); each Playgama action separately | `/authorize-publish draft` · `sandbox` · `catalog-update` · `traffic` |
| Moderation | not available via MCP | do it in the Playgama console (the orchestrator gives exact steps) |
| Archive | records copied to `archive/` and the game repo | `/archive-game` |
| Abandon a draft | a game before development (IDEATION, CONCEPT_APPROVED, SPEC_DRAFT, SPEC_APPROVED) is dropped → ABANDONED, then archived → ARCHIVED | `/abandon-game <reason>`, then `/archive-game` |

Other: `/game-new <idea>`, `/game-status`, `/game-focus <id>`, `/resume`, `/approve-spec-change`, `/factory-metrics`.

**Abandoning a draft game (FX-15).** A game that never reached development (for example one superseded by another idea) leaves the active list through two human gates:

```
IDEATION | CONCEPT_APPROVED | SPEC_DRAFT | SPEC_APPROVED --/abandon-game <reason>--> ABANDONED --/archive-game--> ARCHIVED
```

1. Type `/abandon-game <reason>` with the game focused, or `/abandon-game <game-id> <reason>`. Only the FIRST word can name the game, so a reason like "superseded by other-game" never selects other-game. The hook refuses the command without a reason. The orchestrator runs `factory gate abandon-game --game <id> --reason "<reason>"`. It is refused in DEV_AUTHORIZED or later (out of scope), with an open change request, with unfinished tasks or live agent claims; a refusal does not use up the approval. Mode → `ABANDONED` (event `game.abandoned` with the reason and the previous mode); design files can no longer be edited.
2. Type `/archive-game`; the orchestrator runs `factory gate archive-game --game <id>`. Records go to `archive/<id>/abandoned-<YYYYMMDD>/production/` (event log, state snapshot and reports of the game; the date is the UTC date of the abandon event) and `archive/<id>/abandoned-<YYYYMMDD>/design/` (a copy of `games/<id>/design/`). In the game repo `production/` and `design/` are committed. Mode → `ARCHIVED`; `status` shows the game in the compact form (`status --brief` hides it unless it is focused).

Nothing is deleted: the game repo `games/<id>/` and the factory state of the game stay and remain inspectable. `/archive-game` for a draft that is not abandoned yet is refused with the hint to type `/abandon-game` first. `/game-focus <id>` moves the focus to another game.

**Publication covers.** After `release package` the orchestrator runs `node factory/cli/factory.mjs publish covers --game <id>` (needs Google Chrome, or `PW_CHANNEL=bundled`, and the Playwright of the game's `.worktrees/<id>/_release-<version>`). It serves the packaged zip (its sha256 must still equal the package record), waits for `game_ready`, follows the optional `covers` scenario of the game's `factory.game.json` (`query`, `settleMs`, `readyTimeoutMs`, `steps` of `press` / `clickAt` / `waitMs`) and writes `square.png` 800x800, `portrait.png` 1080x1920, `landscape.png` 1920x1080 and `covers.json` into `.inbox/<id>/publication/covers/`; the hashes are also recorded as a `publication.covers` event. The release-manager only references these paths in `packet.json`; `publish prepare` refuses covers from any other folder, edited covers and covers made for another build. The covers are raw gameplay screenshots; title overlays with the official `covers.mjs` (puppeteer) are optional and not part of the factory flow. The scenario file `factory.game.json` is a protected file for task agents, so changing a game's scenario needs a factory-authorized change. If no `game_ready` signal can be observed (a game that bundles its own Bridge is invisible to the page hook; `?pgtest=1` in the scenario query makes it observable), the shot is taken once the canvas is up and recorded as `readySignal: "canvas-only"`; `publish prepare` refuses such covers unless the orchestrator re-ran the command with `--accept-canvas-only` after checking the shots (the acceptance is recorded in `covers.json` and the event).

**Only typed commands count as approvals.** "Yes, go ahead" (or "Да, делай") in chat is not an approval; the orchestrator will tell you which command to type. Each approval is bound to the exact artifact you saw — if it changes afterwards, you are asked again.

## 3. Where to look
- Status: `/game-status` or `node factory/cli/factory.mjs status`
- Phase reports: `.factory/games/<id>/reports/` (data) and `.inbox/<id>/reports/` (narrative)
- Audit of your decisions: `node factory/cli/factory.mjs decisions`
- Metrics: `node factory/cli/factory.mjs metrics`
- Game code: `games/<id>/` (main = releases), integration build in `.worktrees/<id>/_integration`
- Release archives: `archive/<id>/<version>/`
- Factory changes in progress: `node factory/cli/factory.mjs maint list` (section 6)
- Reviews: one strictly validated schema for every review (game tasks and factory maintenance), owned by `factory/cli/lib/review-schema.mjs`. `node factory/cli/factory.mjs review schema` prints it with a filled example; `review check <file> [--task <id> --game <g>]` validates a draft without recording anything (reviewers run it before finishing). For a verified task the orchestrator runs `task review-packet <id>`, which writes `.inbox/<id>/<task>/review-packet-a<n>.md` for the reviewer; `task review <id>` refuses an invalid review and lists every problem with its exact path.
- Plans: `plan validate <file>` (read-only; agents may run it) checks a plan. It prints `WARNING: L-01` when one task owns a whole test tree with more than `planTestTreeMaxCriteria` (default 25) acceptance criteria; the architect then splits e2e work into flows / viewports / quality tasks. Amendments (`.inbox/<id>/plan/amend-<slug>.json`) add `tasks` to phases that are not approved and `modify` PENDING, never-started tasks (each given field replaces the whole value: `title`, `description`, `acceptance`, `inputs`, `outputs`, `tests`, `risk`, `deps`, `scope`, `agent`, `reviewer`). `plan validate <file> --amend --game <id>` checks an amendment against the current plan and prints before/after; `plan load <file> --amend` applies it (`plan.amended` event, quoted in the phase data report). If a task started between validation and load, the load is refused with a clean error; add a corrective task instead.

### Assets (library, remote index, preview)
Storage layers:
- **Remote index** (metadata only, no bytes): one SQLite file on D:, `.cache/asset-index/index.sqlite` (env `GAME_ASSET_INDEX` overrides). Rebuildable at any time; never edited by hand (the guard refuses it). `assets sources`, `assets sync` and `factory doctor` show its path and schema version.
- **Library** (bytes of acquired / ingested packs, `PACK.json` per pack, `catalog/catalog.jsonl`, `catalog/denylist.jsonl`): Google Drive for desktop, folder named by `GAME_ASSET_LIBRARY` (local fallback `.cache/asset-library`). PACK.json is authoritative (verification included); the catalog is append-only and rebuilt from the manifests by `assets reindex`.
- **Origins**: the indexed sources (OpenGameArt mirrors on Hugging Face: `oga-cc0`, `oga-cc-by-3`, `oga-cc-by-4`); bytes are fetched only for chosen items (`acquire`, `preview`).
- **Drive cache on D:** Drive for desktop streams files through its local cache; put that cache on D: (Drive → Settings → Advanced → Local cached files directory). `factory doctor` reads the configured path from the registry and warns under 10 GB free.

Flow (asset-producer; any agent may run `search`, `show`, `sources`, `stats`, `pull` and `--help` of every subcommand): `assets search` → `assets search --remote` → `assets preview <ids> --out .cache/asset-preview/x.png` → `assets acquire <remote-id>` → check the page (AS-04) → `assets verify <source/pack> --evidence "..."` → `assets pull <ids> --task <T>`. `assets deny <id|author> --reason "..."` blocks an item or author (search skips it, acquire and pull refuse it). `assets stats` shows totals, per source and per pack (verified / declared).

Optional environment: `HF_TOKEN` (Hugging Face token: higher rate limits for `sync` / `acquire`; never logged), `GAME_ASSET_INDEX` (index file), `GAME_ASSET_PREVIEW_CACHE` (preview temp folder), `FFMPEG` / `FFPROBE` (binaries; preview and audio measurements need them).

Rebuild the index: delete `.cache/asset-index/index.sqlite` (or leave it) and let the asset-producer run `node factory/cli/factory.mjs assets sync all` (about a minute; measured sizes are re-learned on the next acquire / preview). Rebuild the catalog from the pack manifests: `assets reindex`.

## 4. Recovery
After a crash, restart or usage-limit interruption just open Claude Code again: the SessionStart hook reconstructs state from `.factory/` and lists recovery actions (including open factory maintenance items). Manual check: `node factory/cli/factory.mjs recover` (`--apply` performs only safe repairs: stale locks, aborted merges, stale agent entries, stale verification markers).

Stopped or crashed agents (claims, FX-02). An agent stopped with TaskStop (or crashed) never reports SubagentStop, so its task claim stays registered. Claims are attempt-scoped:
- `factory task start` of attempt N supersedes every claim of that task from an earlier attempt: those agents are marked inactive, their writes (worktree, inbox, git) are denied ("superseded by attempt N") and they never block the claim of attempt N.
- To re-run the SAME attempt with a fresh agent (the agent stopped mid-attempt), the orchestrator runs `factory task release-claim <ID> [--agent <agentId>] --reason "..."` (factory maintenance: `factory maint release-claim <FX-ID>`), then re-dispatches the attempt's `Dispatch to` agent with the same packet. The release is logged (`task.claim_released`, with who, agent id and reason); the released agent's writes are denied from then on. Only the orchestrator may run it.
- The Agent concurrency cap (`maxActiveAgents`) and `status` (`live agents`) count only active agents whose claim is neither superseded nor released.
- `factory recover` reports `stale-claims` (active agents whose claim is superseded or released, or whose task is no longer in progress; `--apply` deactivates them regardless of age), `stale-agents` (unclaimed agents active for > 3 h; `--apply` deactivates them) and `long-claim` (a live claim held for > 3 h: never cleared automatically; release it only when the agent is really gone).

What `recover` reports for running and interrupted work:
- `verifying` — a task is SUBMITTED and its verification marker (`.factory/games/<id>/runs/verify-<task>.json`: pid, host, start, attempt) belongs to a live process: verification is still running. Wait; a second `task verify` / `task submit` is refused ("verification already running, pid N, started …").
- `submitted-unverified` — SUBMITTED with no marker or a marker of a dead process (interrupted), or the last run hit an infrastructure failure: re-run `factory task verify <task>`.
- `integrating` / `stale-integration-lock` — the integration lock belongs to a live process (wait) or to a dead one (broken automatically by the next `task integrate`).
- Infrastructure failures (port in use / `EADDRINUSE`, browser missing or failed to launch, `ENOSPC`, install network errors; the list is data: `INFRA_SIGNATURES` in `factory/cli/lib/runs.mjs`) do not consume an attempt: the task stays SUBMITTED (`task.verify_infra_failed`, evidence `verify-infra-<k>.json`). Fix the environment and re-run `task verify`. Test failures and timeouts are never treated as infrastructure; signatures are matched only in the last 30 lines of the failed step's output. This is bounded: an attempt gets at most `infraRetriesPerAttempt` (`factory/config.json`, default 2) infrastructure-classified runs; the next matching failure is a normal VERIFY_FAILED (`repeated-infrastructure`) that consumes the attempt and follows the usual retry/blocker path, because a failure that repeats is most likely caused by the task's code.
- Marker whose pid was reused: markers and port reservations count as live while their pid exists (and always for the first 5 s, or while unreadable, up to 3 h). Windows reuses pids, so after a hard kill an unrelated process can keep a task in `verifying`. Check the pid (`tasklist /FI "PID eq N"`); if it is not a factory `node` verify, run `node factory/cli/factory.mjs recover --apply --clear-verify-marker <TASK> --game <id>` (orchestrator only; the marker is archived under `.factory/games/<id>/runs/cleared/`), then `task verify <TASK>`.
- Ports: every factory run reserves a free port (`.factory/ports/<port>.json` while it runs) and passes it to all its steps as `E2E_PORT`; it is recorded as `port` in the run's evidence. When you or an agent run Playwright by hand, set a random `E2E_PORT` (one-liner in `factory/templates/game-phaser-ts/GAME_CONVENTIONS.md`).

### Verify checks: external URLs (FX-17)
- `no-external-requests` scans the lines a task adds under `src`, `index.html` and `public` for `http(s)://` URLs. A URL passes when it matches a regex in `urlAllowlist` of the game's `factory.game.json` (the template allows `localhost` and `bridge.playgama.com`). A failure lists every URL as `<file>: <url>`.
- Plain-text licence/notice files are skipped per file, by basename only: `OFL|LICENSE|LICENCE|COPYING|NOTICE|CREDITS|ATTRIBUTION` (optionally followed by `.`, `_` or `-` and a suffix, e.g. `OFL-FAQ.txt`) with extension `.txt` or `.md`, or with no extension (`LICENSE`, `COPYING`). They ship for legal reasons (OFL section 2) and are never loaded by the game. Code and markup (`.js`, `.ts`, `.html`, `.css`, `.json`, `.svg`, ...) are always scanned, whatever their name (`src/license.ts`, `public/OFL.js`). The template build validator (`validate-build.mjs`) only inspects `index.html` references and analytics hosts, so it needs no such exclusion.

## 5. Models
Subagent models are **pinned** in their definitions (`.claude/agents/*.md`). The single source of truth is the `models` table in `factory/config.json`; `node factory/cli/gen-agent-models.mjs` applies it and `factory doctor` checks it.

| Agent | Model | Effort |
|---|---|---|
| game-developer, platform-engineer, qa-engineer, asset-producer | `claude-sonnet-5-5` | high |
| release-manager, market-analyst | `claude-sonnet-5-5` | high |
| tech-architect, code-reviewer, game-designer | `claude-opus-5-5` | medium |
| game-developer-retry, platform-engineer-retry, qa-engineer-retry, asset-producer-retry | `claude-opus-5-5` | medium |
| game-orchestrator (main session) | not pinned; default `claude-opus-5-5`, effort high (`.claude/settings.json`) | — |

- Attempt 1 of a task runs as the task's agent; attempts 2 and later run as its `-retry` variant (same instructions and tools, Opus). `factory task start` prints `Dispatch to: <agent>`; the guard refuses a claim by any other agent type and refuses any Agent call that passes `model` or `effort`.
- The `-retry` files are generated from the base definitions; never edit them by hand. To change a pin or an agent's instructions: edit `factory/config.json` (or the base `.md`), run `node factory/cli/gen-agent-models.mjs`, run `factory doctor`. This is a factory change (see section 6).
- Changing the orchestrator model: for the current session type `/model <model>` and `/effort <low|medium|high|xhigh|max>`. Durably on this machine: put `"model": "<model>"` (optionally `"modelSettings": {"<model>": {"effortLevel": "<level>"}}`) into `.claude/settings.local.json` (gitignored; it outranks `.claude/settings.json`).
- Avoid the environment variables `CLAUDE_CODE_EFFORT_LEVEL`, `CLAUDE_CODE_SUBAGENT_MODEL` and `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`: they override the pinned subagent models/effort for every agent. `factory doctor` shows `WARN` when one is set in the environment or in the `env` block of `.claude/settings.json` / `.claude/settings.local.json`, and names where. Remove it and restart Claude Code.

## 6. Maintenance
- Shared kit: change `packages/pg-kit`, bump its version, `node factory/cli/factory.mjs kit pack` (immutable release). Existing games keep their pinned kit; upgrades are explicit tasks.
- Template (`factory/templates/game-phaser-ts`, version = `templateVersion` in its `factory.game.json`): `node factory/cli/factory.mjs template check game-phaser-ts` must pass after any template change. Since 1.1.0 the template pins `packageManager` (pnpm), ships `.gitattributes` (stored as `_gitattributes`), wraps key handlers with `dedupeKeyEvents` (Phaser 4.2.1 key replay) and has real-key e2e tests without fixed sleeps; 1.1.2 adds `pnpm-workspace.yaml` (relative `storeDir`, FX-16). `GAME_CONVENTIONS.md` is the agents' rulebook. Existing games keep the template they were scaffolded from.
- Factory tests: `node --test factory/cli/test/*.test.mjs` (one file per change: `lifecycle`, `fx-models`, `fx-NN`) (pass the files, not the directory: `node --test factory/cli/test/` fails on Node 24); kit tests: `corepack pnpm test` in `packages/pg-kit`.
- Agent definitions: `node factory/cli/gen-agent-models.mjs --check` (also part of `factory doctor`).
- Plugin updates: `claude plugin marketplace update playgama-plugins` then `claude plugin update playgama-developer-cabinet@playgama-plugins`; re-check `factory/knowledge/playgama-verified.md` (tool list) and `factory/cli/lib/approvals.mjs` (op map) if tools changed.

### Factory changes (maintenance worktrees)
Changes to the factory itself (CLI, hooks, agents, skills, templates, docs) are implemented by a specialist in an isolated worktree of the factory repo and merged into `main` only by the orchestrator after an independent review:
1. The orchestrator writes the brief to `.inbox/_factory/<FX-ID>/brief.md` and runs `node factory/cli/factory.mjs maint start <FX-ID> --agent <type> [--reviewer <type>] --brief <file>`. This creates `.worktrees/_factory/<FX-ID>` on branch `fx/<FX-ID>` from `main`, records it in `.factory/maintenance.jsonl` and writes the packet `.inbox/_factory/<FX-ID>/packet-a1.md`.
2. The implementer claims it (`maint claim <FX-ID>`); it may write only in that worktree and in `.inbox/_factory/<FX-ID>/`, runs the tests there, commits on `fx/<FX-ID>` and writes `report-a1.json`. It cannot stop without the report.
3. The reviewer (default `code-reviewer`, always a different role) writes `review-a1.json` with the reviewed commit sha, in the unified review schema (maintenance profile: `head` required; criteria are the acceptance ids of the brief's "Acceptance" section, if it has one) and self-checks it with `review check <file> --task <FX-ID> --game _factory`.
4. `node factory/cli/factory.mjs maint merge <FX-ID>` merges with `--no-ff` only if: the report and the review were written by the recorded agents, the verdict is ACCEPT without critical/major findings and covers the current branch head, the worktree is clean, the branch contains the current `main`, the root checkout is on `main` with nothing staged and no local file the merge would overwrite, and `factory/config.json` → `maintenance.verify` (default: the factory test suite) passes in the worktree. Every refusal says what to do next.
5. After the merge the orchestrator runs `factory doctor` (and `factory template check game-phaser-ts` when relevant) and reports to you. Worktrees and branches are kept (history is never deleted).
- `maint list` / `maint show <FX-ID>` show the state and the next step. Agent-definition or settings changes may need a Claude Code restart.
- Interruptions: `factory recover` (and the SessionStart context) reports `maint-unrecorded` (a `.worktrees/_factory/<FX-ID>` without a record, left by an interrupted `maint start`: you inspect and remove the worktree and branch, then the orchestrator starts again) and `maint-merged-unrecorded` (the branch is already in `main` but not recorded, left by an interrupted `maint merge`: `maint merge <FX-ID>` re-checks report and review and records the existing merge).
- Subagents may run git write commands (commit, add, stash, merge, reset, …) only when the effective directory (hook cwd, then `cd`/`-C`) is inside their claimed worktree; read-only git (diff, show, log, status) is always allowed.

### Concurrency and host load
`factory/config.json`: `concurrency` (default 3) caps the tasks in progress per game (`task next` free slots). `maxActiveAgents` (default 4) caps live subagents, reviewers included; the guard refuses further Agent calls. Host load matters: each running task does its own `pnpm install`, build and Playwright runs, and each factory verify adds another build and browser. On a slower host or with little RAM, lower both values (e.g. 2 and 3) through a factory change. The CLI and the guard read the config on every call, so no restart is needed. Typical overload symptoms: e2e timeouts and frame-pacing failures in verify that pass when run alone.

### Guard refusals and the agents' shell
- A `[factory]` guard refusal is final for that action. Every agent definition says so: agents never rephrase, obfuscate or route around it; they quote it in their report or review and continue with what is allowed. Reviewers that need a probe run existing tests in the worktree under review (`node --test <file>`, the game's unit/e2e commands) or report the limitation. A refusal that blocks legitimate work is a factory defect: fix it with a factory change, never by working around it.
- Spec mode (FX-05): while a game is CONCEPT_APPROVED / SPEC_DRAFT or a change request is open, asset-producer writes `design/spec/art-audio.md` and qa-engineer writes `design/spec/test-plan.md` without a task claim (their `-retry` variants too); every other write of theirs needs a claimed task. Full ownership table: the `factory-spec` playbook.
- Shell guard (FX-05, `factory/cli/lib/shell.mjs` + `shell-rules.mjs`): the guard parses each Bash/PowerShell line into simple commands and relaxes the old text rules only for lines it fully understands: known readers, the modelled writers (cp, mv, mkdir, tee, …), cd, git with known subcommands, `node <script file>`. For those lines, `2>&1`, `| head`, heredoc commit messages, reads of `factory/cli/...` paths and copies out of `.inbox/` are no longer refused. Lines it does not understand keep the old strict text rules, with their false positives: shells and interpreters running code from a string or stdin (bash/sh/pwsh/cmd, eval, `node -e`, xargs, `find -exec`, npx), wrappers, odd or unterminated quoting, `corepack pnpm ...`, loops. Copy/move arguments naming `.factory/` or `.inbox/` are refused, except the plain first source of a copier, so copy one file per `cp <src> <dst>`. Agents write into `.inbox/` and `.factory/` with the Write tool or the CLI only.
- Shell guard known limitations (follow-up, see STATUS): the approval-key, `claude`, push and destructive-git checks still match the whole command text, so they can be dodged with quoting and still refuse a commit message that mentions those words (use `git commit -F <file>`). `git config` is not treated as a write. `tar --remove-files`, xcopy/robocopy and hard links (`ln`, `mklink`) are not modelled. Protected-tree deletes are matched as text only. Scripts in files and git hooks are not inspected.
- On Windows the agents' Bash tool sets `MSYS_NO_PATHCONV=1`, which breaks the `corepack`/`pnpm` shell shims (ENV-01), so agents run `corepack.cmd pnpm ...` there. Your own terminal and the factory CLI (which runs commands through cmd.exe) are not affected.
- Caches and temp files stay inside the factory (FX-16). The same `MSYS_NO_PATHCONV=1` passes POSIX paths unconverted to native programs: `/tmp/x` (also what a bare `mktemp -d` returns) becomes `D:\tmp\x` and `/c/Users/...` becomes `D:\c\Users\...`. Agents therefore use `<root>/.cache/tmp` for scratch (`mktemp -d -p "<root>/.cache/tmp"`), pass `D:/...` paths (or `cygpath -m`) to node/git/pnpm, and install packages only through the configured commands. The PreToolUse guard adds a hint (never a refusal) to a Bash line with a bare `mktemp` or a `/tmp` / `$TMPDIR` argument of node/git/pnpm. The CLI uses `<root>/.cache/tmp` too (`paths().tmp`, env `FACTORY_TMP_DIR`) and exports `TMPDIR`/`TEMP`/`TMP` pointing to it in every spawned command.
- pnpm store: pnpm 11+ ignores `npm_config_store_dir` and `.npmrc` `store-dir`; with no store configured it creates `<drive root>\.pnpm-store`. The CLI sets `pnpm_config_store_dir` (it wins over files), and `pnpm-workspace.yaml` files pin `storeDir` for direct calls: the factory root (`.cache/pnpm-store`), `packages/pg-kit` (`../../.cache/pnpm-store`) and the game template (`../../../.cache/pnpm-store`, relative so no machine path is committed into game repos; right for every depth-3 checkout: `.worktrees/<game>/<task>`, `.cache/template-check/<run>`, `factory/templates/<t>`). The bare `games/<id>/` checkout (depth 2) is never installed into; there only the environment applies. If `.claude/settings.local.json` sets `npm_config_store_dir`, also set `pnpm_config_store_dir` (`factory doctor` warns).
- `factory doctor` lists stray directories at the drive root of the factory (`.pnpm-store`, single-letter dirs such as `c\Users\...` from MSYS paths, `tmp` holding `mktemp`/factory content) with their size and a cleanup hint, and the size of `.cache/tmp` with the entries older than 7 days. It never deletes anything; you remove them by hand after checking (e.g. `rmdir /s /q D:\.pnpm-store`).
